本报告汇总已有构建记录、真实桌面验证和最近三次资源测量，不代表整理报告时重新运行了应用或模型。原始时间采用执行主机记录的 UTC；资源测试记录中的 `2026-10-27` UTC 对应当时主机 UTC+8 的 `2026-10-28`，不以文件名推断其他时区的日期。

## 1. 结论与适用范围

应用侧连接修复已经通过真实 Snow Shot 桌面进程的模型检测、对话和流式翻译检查；35B 原有修复在当时的桌面回归中保持有效。后续资源测试仅向 2B 发起请求，未操作 35B。

Qwen3.5 2B 在 Q8_0、4096 上下文配置下，48 轮普通连续翻译的物理内存采样峰值为 **1.493 GiB**；6 轮接近上下文上限的翻译为 **0.953 GiB**。两组专用显存峰值均为 **2.952 GiB**，共享 GPU 内存峰值均为 **0.584 GiB**。

近满组实际输入加输出达到 4019–4064 token，即配置容量的 98.12%–99.22%，但 **6 轮中有 5 轮达到请求设置的输出上限而截断**。它证明了近满 token 负载下的资源读数，不能写成 6 轮完整翻译通过。

两组轮数、输入组织、进程生命周期及缓存历史不同，不能由近满组较低的 RSS 推断“长文本更省内存”。所有峰值均限定于对应采样窗口，不是所有输入、并发或长期运行的绝对上限。

**物理内存**使用 Windows 进程工作集 RSS / Working Set。**专用显存、共享 GPU 内存**使用 Windows PDH `GPU Process Memory` 按 PID 读取，再汇总该 PID 的 GPU 实例。48 轮测试时，NVIDIA 查询将受测 PID 对应到 RTX 3060；WDDM 下每进程 `used_gpu_memory` 返回 `N/A`，因此没有以整卡总占用代替 2B 的用量。

共享 GPU 内存与 RSS 是不同计量口径，不能直接相加。私有提交量也不等于实际驻留物理 RAM。下文采用 GiB，1 GiB = 1,073,741,824 字节。

## 3. 应用连接修复及桌面验证

### 3.1 已复现的问题与应用侧处理

已有修复记录中的对照结果是：2B 的 `/v1/models` 不带 Origin 时返回 200，带 `Origin: http://tauri.localhost` 时返回 403；35B 在两种请求下均返回 200。本次已复现的 2B 失败路径因此与 WebView Origin 的接受条件有关，不能简单归因于模型未运行或缺少 API Key。

修复保留了 35B 的 IPv6 URLPattern 冒号转义，并在应用侧统一模型传输：

- 已锁定的 `tauri-plugin-http 2.5.4` 启用 `unsafe-headers`，未升级插件。
- `modelFetch` 仅对 HTTP/HTTPS 回环地址 `127.0.0.1`、`localhost`、`[::1]` 传入空 Origin，使原生请求移除该头；回环请求禁止自动重定向。
- 模型检测、对话和翻译使用统一传输入口，保留请求体、鉴权头、取消信号及流式交付；401 与 403 分别显示认证失败和服务拒绝访问。
- 未扩大 URL allow scope 或关闭 TLS 验证。`unsafe-headers` 是插件全局编译特性，回环地址限制在应用封装中实现，不能描述为 Rust 侧新增了隔离机制。

## 4. 单次快照：此前 1.06 / 2.19 GiB 的含义

此前会话工具输出中，已加载 2B 推理进程的物理内存为 1,141,817,344 字节，约 **1.06 GiB**；Ollama `/api/ps` 的 `size_vram` 为 2,356,234,156 字节，约 **2.194 GiB**。这是一个时间点的快照，不是连续翻译峰值。

该进程私有提交量约 4.72 GiB，不能当作全部物理 RAM。Ollama 主进程当时额外约 54 MiB，也不应并入本报告的“仅 2B 推理进程”统计。

后续两组测试中，Ollama 仍报告约 2.194 GiB，而 Windows 整个 2B 推理进程的专用显存计数器达到 2.952 GiB。两者统计值不同；本报告不把 2.194 GiB 当作完整进程显存峰值，也不推断差额的具体组成。初始快照的来源是会话中的工具输出，不是归档中的连续采样文件。

## 5. 普通连续翻译：48 轮

测试分为 12 轮和 36 轮两批；两批使用相同推理进程 PID 20248。原始记录范围为 `2026-10-27T17:43:19.642600Z` 至 `2026-10-27T17:47:09.636512Z`，中间存在批次间隔；不能将整个时间跨度写成无间断压力测试。

两批各自连续采样 57.91 秒、131.86 秒，合计约 189.77 秒、1686 个采样点，包含首批加载及批内前后观察时间。输入为 57–716 英文单词，实际输入 110–866 token、输出 54–363 token；每轮实际输入加输出合计为 164–1226 token，未接近 4096 容量上限。

48 轮均收到 HTTP 200、非空流式文本及 `done_reason=stop`。长输入由有限段落组合，含重复内容，模型对部分重复段落进行了合并；自然结束不能单独证明每段都完整翻译。

## 6. 接近 4096 容量的连续翻译：6 轮

本组开始前模型已按原有空闲策略自然卸载，首个请求触发正常加载，受测推理进程为 PID 14900。校准与正式测试共用该进程，没有显式卸载、重启或改变缓存策略。

两次校准的实际输入加输出分别为 1918 + 1585 = 3503 token、2159 + 1877 = 4036 token，均自然结束；每次校准前另有一个 `num_predict=1` 的 token 计数预检。这四个请求与正式 6 轮分开记录，不混入正式阶段的资源峰值。

## 7. 两组峰值比较及解释边界

| 指标 | 普通连续翻译 48 轮 | 近满容量翻译 6 轮 | 差值 |
|---|---:|---:|---:|
| 物理内存 RSS | 1.493 GiB | 0.953 GiB | -0.540 GiB |
| 专用显存 | 2.952 GiB | 2.952 GiB | 0 |
| 共享 GPU 内存 | 0.584 GiB | 0.584 GiB | 0 |

可以确认：在这两组记录中，把实际 token 总量提高到约 98%–99% 容量，没有观察到专用显存或共享 GPU 内存计数器峰值上升。

不能确认：实际 token 总量是两组 RSS 差异的原因。普通组与近满组分别使用不同轮数、不同长度输入与同一长文重复输入、不同的新建进程和缓存历史；没有控制这些变量，不能给出因果结论或推广为统一内存预算。

显存数字来自 Windows 进程计数器，没有用 WPR/ETW 独立核验，也不能排除计数器误差或采样点之间的瞬时峰值。短时间内趋于稳定不证明长时间运行无泄漏。
